# Same-Owner Original Watering Maintenance

## Accepted Parent And Scope

PR529 accepted original watering result/prefix/resource verification and shared
evidence kernels. This successor attaches that sealed result to the **existing**
persistent crop phase owner. It does not dispatch a watering tool, replace the
executor, complete a day/save cycle or enable automatic managed operation.

`AdmitWateringMaintenanceAsync` consumes an already completed original native
transition. It binds the current accepted full source/ledger, original run plan
and active covered commitment identities, exact run/executor, all native inputs
and original marker intent under the same gate/OS lease/sequence/pending head.
It reopens the original `CropTeacherWateringMaintenance` verifier rather than
accepting a caller-provided interface implementation or a summary success flag.
Unknown future maintenance execution protocols cannot enter this completed scope.

## Shared Transaction, Distinct Kind

`ICropTeacherSupportingTransition` exposes the existing route/watering result's
original full ledger, marker/reply verifier, after and input guard. Both concrete
witnesses remain sealed. The owner chooses actual witnesses internally; it does
not grant models, callers or arbitrary interface implementers native authority.

The original route marker invocation/readback and recovery body is shared, not
copied. `RunSupportingRouteAsync` preserves its route-only API, intent schema,
filename and original defaults. `RunWateringMaintenanceAsync` selects the new
`watering_maintenance` kind, `crop_teacher_managed_watering_start.v1` claim and
`maintenance-intent.json`; it is not a route alias. Non-seed preparation/dispatch
guards use the actual common classification, so maintenance cannot enter seed
callbacks or trigger another original route compilation while pending.

The shared flow preserves original ordering: claim one marker invocation, retain
the exact intent, read/compare full original base, validate inputs, use the
original journaled commit, independently replay the complete original reply and
read back full final authority before advancing. It does not claim the earlier
native action was dispatched by this adapter. A claimed unknown marker is not
called zero, cleared or resent.

Accepted watering evidence records the actual verified tile count/list and
`complete_batch`, not whole-day/crop completion. It has no route-target/native-route
claim fields. Counts and tiles are independently reconstructed on reopening,
never trusted merely because the accepted JSON says success. Crop/resource owners
and outstanding obligations stay unchanged apart from the original marker's
source/revision/history semantics. Formal training and preference eligibility stay
false; a partial prefix is not a completed batch or a negative preference label.

## Recovery And Continuation

- Admitted but not marker-claimed maintenance may make its first original marker
  call once after a process restart.
- Lost marker reply uses the original journal/lookup before final full Get. An
  existing bad reply or missing original journal is not overwritten or retried.
- Lost acceptance acknowledgement reconstructs the original accepted head and
  restores authority without another marker or native invocation.
- Every source/queue/receipt/retained step is pinned. Foreign run/executor/coverage,
  changed inputs, unrelated backend mutations and incompatible callback families
  fail before an invalid acceptance or additional mutation.
- A subsequent original owned route uses the same sequence and current accepted
  watering head. Mixed head restart remains the same owner, not another scheduler.

The shared recovery file now follows its actual responsibility as
`CropTeacherManagedSeedOwner.SupportingTransition.Recovery.cs`; there is no second
route/watering copy. Old seed/lifecycle/route serialized contracts and execution
rules are not widened to fit maintenance.
