一、项目定位
--------------------------------------------------------------------------------

本项目不是先做“会自己走路的机器人”，而是先做：

    一个能读取游戏状态、理解当前局势、生成可验证计划、
    记住共同经历、持续聊天的 AI 副官。

第一阶段由玩家手动执行计划。
后续逐步加入自动执行能力。

最终目标：

    副官版
        ↓
    规划版
        ↓
    半自动版
        ↓
    完整 AI 队友
        ↓
    具备长期记忆、偏好学习和协作能力的陪玩智能体

核心原则：

1. 第一版就固定核心接口。
2. 后续升级只新增模块，不推翻核心结构。
3. LLM 不直接控制游戏。
4. 所有操作先经过规则验证。
5. 所有事实必须来自真实游戏状态。
6. 聊天人格、规划器、执行器共享同一份状态和记忆。
7. 不追求“绝不犯错”，而追求“错误可检测、可中止、可恢复”。


二、最终数学模型
--------------------------------------------------------------------------------

采用：

    约束型因子化半马尔可夫决策过程
    Constrained Factored Semi-Markov Decision Process

并结合：

    Options 分层动作模型
    HTN 风格任务分解
    Safety Verifier 安全验证器
    Preference Ranker 偏好排序器
    Behavior Tree 行为树执行器


统一写作：

    M = <S, O, Pτ, R, C, γ>

含义：

    S   = 状态空间
    O   = 高层动作 Options
    Pτ  = 执行动作后，经过不定时长到达新状态的转移模型
    R   = 奖励函数
    C   = 硬约束和安全约束
    γ   = 长期折扣因子

为什么不用普通 MDP：

    星露谷中的动作持续时间差别极大。

例如：

    走一格：几秒
    收一片农田：几十分钟
    去商店采购：数小时
    下矿：可能占用一整天

因此高层动作必须允许不同持续时间。
SMDP 比普通 MDP 更适合。

--------------------------------------------------------------------------------

推荐架构：

    SMAPI / Save / Game Events
                ↓
          World Adapter
                ↓
       Canonical State Store
                ↓
       Event & Memory Store
                ↓
        Goal Compiler / HTN
                ↓
          CF-SMDP Planner
                ↓

                ↓
            Plan[Option]
             ↙       ↘
      Dialogue Layer   Executor Port
                          ↓

必须固定的四个核心接口：

    2. ActionSpec

只要这四个接口稳定，
副官版升级为完全体时就不需要整体重构。

五、Option 高层动作接口
--------------------------------------------------------------------------------

每个高层动作统一定义：

    Option = {
        id,
        name,
        initiation_conditions,
        goal_conditions,
        estimated_effects,
        duration_model,
        policy,
        success_conditions,
        abort_conditions,
        recovery_policy,
        safety_constraints
    }

示例：

    option: visit_pierre_and_buy_seeds

    initiation_conditions:
        season == summer
        pierre_shop_open == true
        money >= estimated_cost
        inventory_has_space == true

    goal_conditions:
        inventory.melon_seeds >= target_count

    estimated_effects:
        money -= target_count * 80
        inventory.melon_seeds += target_count
        time += estimated_travel_and_purchase_time

    success_conditions:
        target_seeds_purchased == true

    abort_conditions:
        shop_closed == true
        insufficient_money == true
        inventory_full == true
        festival_override == true

    recovery_policy:
        stop_execution
        return_control_to_user
        explain_failure
        request_replan

    safety_constraints:
        never_sell_protected_items
        never_spend_reserved_money
        never_continue_after_state_mismatch


六、任务分解：HTN
--------------------------------------------------------------------------------

HTN 只负责任务分解，不直接做最终决策。

示例：

    目标：夏季第一天种满 128 格

    分解：

        prepare_summer_field
            ├─ inspect_field
            ├─ remove_dead_crops
            ├─ count_available_tiles
            ├─ calculate_seed_quantity
            ├─ verify_budget
            ├─ travel_to_pierre
            ├─ buy_seeds
            ├─ return_to_farm
            └─ plant_seeds

HTN 的作用：

    把大目标拆成可验证的小任务。

SMDP 的作用：

    比较多套计划的长期价值。

Safety Verifier 的作用：

    删除非法或高风险方案。

Preference Ranker 的作用：

    在合法方案中选出更适合用户当前状态的方案。


七、安全验证器
--------------------------------------------------------------------------------

绝不能只靠奖励函数惩罚错误。

必须先构造安全动作集合：

    Safe(s) = {
        option |
        PreconditionsSatisfied
        AND InvariantsSatisfied
        AND Recoverable
        AND StateVerified
    }

执行前检查：

1. 前置条件是否满足。
2. 游戏状态是否与计划一致。
3. 动作是否合法。
4. 动作是否可中止。
5. 动作失败后是否可恢复。
6. 是否涉及不可逆操作。
7. 是否可能丢弃关键物品。
8. 是否可能花掉保留资金。
9. 是否可能错过节日或商店时间。
10. 是否存在地图、版本或模组不兼容。

硬约束示例：

    禁止出售标记为 protected 的物品。
    禁止花费 emergency_reserve。
    禁止在状态不确定时执行不可逆操作。
    禁止在路径不可验证时自动移动。
    禁止在 UI 状态未知时自动点击。
    禁止 LLM 绕过规划器直接调用执行器。
    禁止聊天模块修改真实世界状态。


八、奖励函数
--------------------------------------------------------------------------------

不能只奖励利润和速度。

建议：

    R =
        θ1 * goal_progress
      + θ2 * interaction_density
      + θ3 * novelty
      + θ4 * shared_experience
      + θ5 * user_preference_match
      - θ6 * fatigue_cost
      - θ7 * irreversible_risk
      - θ8 * time_pressure
      - θ9 * repetitive_work
      - θ10 * plan_fragility

字段解释：

    goal_progress
        对长期目标的推进程度。

    interaction_density
        当前计划是否提供持续反馈和互动。

    novelty
        是否接触新内容。

    shared_experience
        是否容易产生值得记忆和讨论的事件。

    user_preference_match
        是否符合用户当前模式。

    fatigue_cost
        是否包含大量重复劳动。

    irreversible_risk
        是否存在不可逆损失。

    time_pressure
        是否要求极限赶时间。

    repetitive_work
        是否机械重复。

    plan_fragility
        是否容易因为一个小意外整体失败。


九、用户模式
--------------------------------------------------------------------------------

系统必须支持至少五种模式：

1. efficiency

    目标：
        最大化收益和长期进度。

2. relaxed

    目标：
        有互动，但不追求极限效率。

3. exploration

    目标：
        接触新地图、新事件、新机制。

4. recovery

    目标：
        只处理会造成损失的事项，
        其余安排高互动、低压力活动。

5. social

    目标：
        提高 NPC 互动、事件和共同体验。


十、第一版先训练什么
--------------------------------------------------------------------------------

不要训练完整规划器。
不要训练视觉到键鼠的端到端模型。
不要一开始做强化学习。

第一阶段训练：

    计划偏好排序器
    Preference Ranker

流程：

    规划器生成若干合法候选方案。

例如：

    A. 收益最高
    B. 互动最多
    C. 最轻松
    D. 探索最多
    E. 社交最多

记录：

    系统推荐了什么
    用户选择了什么
    用户拒绝了什么
    用户中途改了什么
    用户最后是否觉得疲惫
    用户是否愿意继续玩
    用户是否认为计划太机械
    用户是否觉得陪伴感更强

训练目标：

    给定当前状态，
    学习用户更可能接受哪一套合法计划。

成对偏好损失：

    L = -log sigmoid(
        Q(state, preferred_plan)
        - Q(state, rejected_plan)
    )


十一、聊天层职责
--------------------------------------------------------------------------------

聊天层必须读取：

    当前 CanonicalState
    当前 Plan
    最近事件
    长期记忆
    用户模式
    失败原因
    安全验证结果

聊天层允许：

    解释计划
    询问用户目标
    评论事件
    生成每日总结
    提醒计划冲突
    发起重新规划
    维持固定人格
    进行自然语言交流

聊天层禁止：

    编造游戏事实
    直接生成执行动作
    绕过 Safety Verifier
    直接修改真实状态
    直接修改长期记忆事实
    猜测未知坐标
    在状态不确定时假装确定


十二、长期记忆
--------------------------------------------------------------------------------

长期记忆不能只放在聊天上下文中。

必须单独保存：

    daily_summary
    important_events
    player_preferences
    recurring_patterns
    long_term_goals
    known_dislikes
    protected_items
    common_mistakes
    current_relationship_context

每日结束生成：

    日期：
    天气：
    完成事项：
    重要事件：
    意外：
    用户状态：
    用户喜欢的部分：
    用户不喜欢的部分：
    明日候选计划：
    未解决问题：
    需要长期记住的事实：

示例：

    第二年春 25 日

    完成：
        购买动物目录
        安装自动收集器
        升级畜棚

    意外：
        误按 Shift 买了 5 本书
        用户选择读档

    用户反应：
        对不可逆错误较焦虑
        对明确可恢复方案接受度高

    明日计划：
        检查施工
        准备夏季种子预算


十三、执行器接口
--------------------------------------------------------------------------------

统一接口：

    ExecutorPort

方法建议：

    validate(option, state)
    preview(option, state)
    execute(option, state)
    pause()
    resume()
    abort()
    rollback_if_possible()
    report_status()
    report_failure()
    request_replan()

第一阶段：

    HumanExecutor

作用：

    只输出清晰步骤，
    由玩家手动执行。

后续：

    AssistedExecutor
        自动计算数量
        自动标记路线
        自动整理信息

    BotExecutor
        执行白名单动作

    FullExecutor
        通过行为树执行复杂动作


十四、行为树
--------------------------------------------------------------------------------

行为树只用于执行器内部。

示例：

    Option：前往皮埃尔购买种子

        Sequence
            ├─ VerifyCurrentState
            ├─ VerifyShopOpen
            ├─ VerifyMoney
            ├─ VerifyInventorySpace
            ├─ PlanRoute
            ├─ ValidateRoute
            ├─ WalkToShop
            ├─ OpenShopUI
            ├─ VerifyProduct
            ├─ ExecutePurchase
            ├─ VerifyInventory
            └─ ReportSuccess

任一步失败：

    立即中止
    保存错误日志
    交还控制权
    请求重新规划


十五、阶段路线
--------------------------------------------------------------------------------

阶段 0：项目骨架

目标：
    建立仓库、数据结构、接口和日志系统。

产出：
    CanonicalState
    ActionSpec
    OptionSpec
    ExecutorPort
    EventLog
    MemoryStore

不得开始：
    自动键鼠
    强化学习
    复杂寻路
    视觉识别


阶段 1：只读副官

目标：
    读取游戏状态并聊天。

能力：
    知道日期、时间、天气
    知道背包、金币、体力
    知道当前任务
    知道作物和动物状态
    生成每日摘要
    保存共同记忆

验收：
    AI 不编造游戏事实。
    重新启动后能恢复近期记忆。
    能回答“今天发生了什么”。


阶段 2：规划副官

目标：
    生成可验证的日程和计划。

能力：
    HTN 任务分解
    候选计划生成
    安全验证
    多目标排序
    不同用户模式

验收：
    能生成至少 3 套合法计划。
    能解释不同计划的取舍。
    能发现商店关闭、时间不足、资金不足。


阶段 3：偏好学习

目标：
    学会用户喜欢哪种计划。

能力：
    记录接受和拒绝
    训练排序器
    根据疲劳和互动需求调整计划

验收：
    一段时间后推荐更符合用户偏好的方案。
    不把所有计划都优化成利润最大化。


阶段 4：辅助执行

目标：
    自动处理无风险信息操作。

能力：
    自动计算采购数量
    自动生成路线
    自动检查库存
    自动生成提醒
    自动标记目标

验收：
    不直接控制角色。
    不执行不可逆操作。


阶段 5：白名单半自动

目标：
    自动执行低风险动作。

候选动作：
    简单跟随
    指定区域移动
    箱子整理
    固定路线
    状态明确的简单交互

验收：
    每个动作都有启动、结束、中止和恢复条件。
    状态不一致时立即停止。


阶段 6：完整 AI 队友

目标：
    自主完成复杂任务并与玩家协作。

能力：
    自主寻路
    自动交互
    任务协作
    行为树执行
    动态重新规划
    玩家意图预测
    长期协作

十八、AI 编程工作方式
--------------------------------------------------------------------------------

用户几乎不具备这一领域知识，因此所有开发任务必须拆成：

    1. 当前目标
    2. 要创建或修改的文件
    3. 完整代码
    4. 运行命令
    5. 预期输出
    6. 验证方法
    7. 常见错误
    8. 回滚方法
    9. 下一步

每次只做一个可验证小目标。

禁止 AI：

    一次生成整个项目
    跳过测试
    跳过接口定义
    跳过错误处理
    擅自重构核心接口
    擅自更换技术栈
    用伪代码代替可运行代码
    省略安装命令
    省略验证步骤


十九、总控提示词
--------------------------------------------------------------------------------

把下面内容发给负责写代码的 AI：

--------------------------------------------------------------------------------

你现在是本项目的首席架构师、实现工程师和测试工程师。

用户几乎不了解：
SMDP、HTN、Options、行为树、SMAPI、C#、Python 后端和安全规划。

因此你必须：

1. 不假设用户具备背景知识。
2. 每一步提供完整可运行代码。
3. 所有命令必须可复制。
4. 所有文件必须说明路径。
5. 每一步必须有验收标准。
6. 每一步必须有失败排查。
7. 不得一次实现超过一个阶段。
8. 不得在未测试前进入下一阶段。
9. 不得修改以下核心接口，除非先解释兼容方案：
   - CanonicalState
   - ActionSpec
   - OptionSpec
   - ExecutorPort
10. 所有升级必须向后兼容。
11. LLM 不得直接控制游戏。
12. 所有执行动作必须通过 Safety Verifier。
13. 所有事实必须来自游戏状态或持久化数据。
14. 不得编造未知状态。
15. 不得使用端到端强化学习作为第一阶段方案。
16. 不得一开始做视觉识别和键鼠模拟。
17. 第一目标是完成只读副官。
18. 第二目标是完成规划副官。
19. 第三目标才是偏好学习。

================================================================================
补充核心：全透明接入 MOD（TransparentBridge）
================================================================================

本项目从第一版开始，就必须通过一个“全透明接入 MOD”读取游戏，
而不是让聊天模型依赖截图、OCR、猜测、存档逆向或零散事件。

该 MOD 是整个系统的底层事实源，也是副官版和完全体之间保持兼容的关键。

建议名称：

    StardewAI.TransparentBridge

项目定位：

    一个开源、可审计、版本化、只提供真实游戏状态与受控操作接口的
    SMAPI 接入层。

它必须做到：

    1. 所有输入可追溯。
    2. 所有状态字段有明确来源。
    3. 所有变化有事件日志。
    4. 所有命令可预览。
    5. 所有执行可拒绝、可中止、可审计。
    6. 未知状态明确标记 unknown，不允许猜测。
    7. 聊天模型不能绕过它直接接触游戏。
    8. 副官版即使用完整透明状态，不允许先做“阉割版接入”。
    9. 后续自动执行只是在相同接口上增加写权限，不重构状态层。
   10. MOD 自身代码、Schema、日志格式和权限规则全部公开透明。


一、全透明的含义
--------------------------------------------------------------------------------

“全透明”不是说必须无条件暴露游戏内部所有私有字段。

工程定义是：

    对于系统已经读取、推断、转换、规划和执行的每一项内容，
    用户和上层模块都能知道：

        它来自哪里
        什么时候读取
        使用了哪个版本
        是否完整
        是否经过转换
        是否存在不确定性
        哪个模块使用了它
        最终产生了什么决定

任何无法稳定读取的字段必须：

    标记为 unavailable
    标记失败原因
    标记适配器版本
    禁止上层假装已知

禁止：

    静默使用反射失败后的默认值
    用 LLM 补全缺失字段
    把推测结果伪装成游戏事实
    隐藏执行失败
    隐藏状态不同步
    隐藏模组冲突


二、MOD 的系统位置
--------------------------------------------------------------------------------

必须改为：

    Stardew Valley
          ↓
    SMAPI
          ↓
    StardewAI.TransparentBridge MOD
          ↓
    Versioned State Snapshot + Event Stream + Capability Manifest
          ↓
    Backend State Store
          ↓
    Planner / Memory / Dialogue / Executor

TransparentBridge 是唯一合法游戏事实入口。

上层禁止直接：

    读游戏进程内存
    读截图猜状态
    绕过 MOD 直接写存档
    直接模拟键鼠
    依赖聊天模型推断游戏事实


三、MOD 必须公开的四类接口
--------------------------------------------------------------------------------

1. Snapshot API

作用：

    返回当前完整、规范化的游戏状态快照。

建议接口：

    GET /api/v1/snapshot

必须包含：

    schema_version
    bridge_version
    smapi_version
    game_version
    installed_mods
    save_id
    player_id
    game_tick
    in_game_time
    real_timestamp
    state_hash
    completeness
    unavailable_fields
    state

要求：

    所有快照可序列化为 JSON。
    相同状态必须得到稳定结构。
    所有对象使用稳定 ID。
    所有枚举使用固定值。
    所有坐标包含地图名和 tile 坐标。


2. Event Stream API

作用：

    实时发送游戏变化，而不是不断传输全量状态。

建议接口：

    WebSocket /api/v1/events

事件示例：

    DayStarted
    TimeChanged
    LocationChanged
    InventoryChanged
    MoneyChanged
    EnergyChanged
    HealthChanged
    CropChanged
    AnimalChanged
    FriendshipChanged
    QuestChanged
    BundleChanged
    BuildingChanged
    MenuOpened
    MenuClosed
    ItemPurchased
    ItemSold
    ItemDropped
    ToolUsed
    InteractionOccurred
    FestivalStarted
    FestivalEnded
    PlayerPassedOut
    SaveLoaded
    Saving
    Saved
    ModListChanged
    StateDesyncDetected

每个事件必须包含：

    event_id
    event_type
    schema_version
    game_tick
    in_game_time
    real_timestamp
    source
    before
    after
    state_hash_before
    state_hash_after


3. Capability Manifest

作用：

    明确当前版本“能读什么、能验证什么、能执行什么”。

建议接口：

    GET /api/v1/capabilities

示例：

    can_read_inventory: true
    can_read_chests: true
    can_read_crop_state: true
    can_read_npc_schedule: partial
    can_read_collision_map: true
    can_read_menu_state: true
    can_preview_purchase: true
    can_execute_purchase: false
    can_execute_movement: false
    can_rollback_purchase: false

每项能力必须包含：

    capability_id
    access_mode
    status
    source
    limitations
    required_permission
    supported_game_versions
    supported_mods
    known_conflicts


4. Command API

副官版默认关闭执行，只保留预览。

建议接口：

    POST /api/v1/commands/preview
    POST /api/v1/commands/execute
    POST /api/v1/commands/abort
    GET  /api/v1/commands/{command_id}
    GET  /api/v1/audit

preview 必须返回：

    command_id
    normalized_command
    required_preconditions
    current_precondition_result
    expected_effects
    irreversible_effects
    estimated_duration
    risk_level
    recoverability
    permission_required
    executable

execute 必须要求：

    通过 Safety Verifier
    状态哈希未变化
    权限允许
    命令未过期
    不存在模组冲突
    不存在未处理的状态不同步

八、只读与写入权限分离
--------------------------------------------------------------------------------

TransparentBridge 必须有权限模式：

    observer
    planner
    assisted
    executor
    developer

observer：

    只读状态
    接收事件
    不允许任何写操作

planner：

    只读状态
    可请求 command preview
    不允许 execute

assisted：

    允许低风险辅助操作
    例如标记、计算、UI 提示

executor：

    允许执行白名单动作
    所有动作必须审计

developer：

    仅开发环境使用
    允许调试接口
    默认禁用

第一版必须运行在：

    observer + planner

即使未来完全体启用 executor，
聊天模型也不能直接获得 executor 权限。

    不允许使用临时简化接口。

二十三、最终结论
--------------------------------------------------------------------------------

最终选型：

    数学底座：
        约束型因子化 SMDP + Options

    任务分解：
        HTN 风格领域模型

    计划搜索：
        Weighted A*
        Beam Search
        或启发式搜索

    第一训练目标：
        计划偏好排序器

    执行控制：
        行为树

    自然语言：
        LLM 只负责目标解析、解释、聊天和陪伴

    记忆：
        独立持久化存储

    安全：
        独立 Safety Verifier

    第一可用版本：
        只读状态 + 规划副官 + 长期记忆 + 聊天

    最终版本：
        可验证、可中止、可恢复的完整 AI 队友


核心目标不是：

    造一个最会赚钱的机器人。

核心目标是：

    造一个知道当前发生了什么，
    记得共同经历，
    能和玩家一起决定下一步，
    并最终能够安全行动的长期陪玩伙伴。
