# Original Crop Supporting-Route Continuity

## Scope And Original Authority

PR526 accepted original incomplete seed preparation continuation. This successor
consumes a **completed original supporting route**, then advances the same managed
owner through the original portfolio marker. It does not dispatch movement, install
another executor, relax idle recapture, or claim that a route finishes a crop cycle.

`CropTeacherSupportingRoute.Open` binds the original run request, accepted source,
full ledger, covered active commitments, original queue/receipt/after and a new step
identity. Crop destination comes from the original layout denominator; sleep
destination comes from the original source home context. Pending material transfers
are rejected. The original owned-supply reader checks all resource owners, not just
the selected crop's seeds.

`MoneyRevenueCropNativeLifecycleProofBuilder.VerifySupportingRoute` reuses the
original identity, queue receipt and supporting-route kernels. The aggregate
lifecycle validator calls the extracted receipt wrapper in its **original position**,
after identity/chain validation. No existing predicate, exception text, day
denominator, control-observation rule or executor changed. Relevant original
receipt kernel: `f61d0991`; route grouping: `c03d524c`/`42a192ef`.

Only original `supporting_route_to_crop` / `supporting_route_to_sleep` kinds qualify.
Allowed movement/connector/wait options and the narrow native sleep-control wait
exception remain the original rules. Receipt identity, exact accepted before,
same-day calendar, destination and the full resource-neutral boundary must all
hold. Inventory, currency, crop state and unknown persistent fields cannot be
washed into recapture or route success.

## Original Ledger Mutation

The new consumer builds a marker-only `ReservationPortfolioCommitRequest` at the
verified after state with the exact old ledger revision and new owned step ID.
No resources are claimed, consumed, moved, released or completed. The original
`ReservationPortfolioCommitEvidenceVerifier` independently replays the full reply.
Crop commitments and every resource reservation remain unchanged, including their
original owner and source identities. Only the original service advances the ledger
source/revision and appends its marker history. No snapshot or source hash is edited.

The rebound boundary can feed the original purchase/transfer/planting scopes.
`CropTeacherLedgerSourceBinder` still rejects unmanaged active crops; the existing
idle-only recapture and seed deadline contracts are unchanged.

## Same Persistent Owner

`AdmitSupportingRouteAsync` verifies completed original native evidence against the
current accepted head, original plan coverage, owner run and executor, then pins
the same sequence/pending admission and exact `route-intent.json` hash. Its phase
kind is `supporting_route`, not a seed preparation or lifecycle closure.

`RunSupportingRouteAsync` holds the same gate and durably claims one marker
invocation before calling the original journaled portfolio commit. It verifies the
full original base, requires the original mutation request/journal, independently
replays the reply and checks the original full final backend readback before
advancing the same owner head. A caller-supplied success flag is insufficient.
Seed preparation/dispatch APIs reject this phase before invoking callbacks.

An admitted but unstarted route can make its first marker call after reopening.
Once invocation is claimed, it is not retried. Pending/head recovery revalidates
the original route and intent, requires the original request/journal and consumes
the retained marker reply, or performs the original read-only mutation lookup if
the reply file is missing. A verified looked-up reply is retained before the full
Get, since later mutations can retire lookup availability. Known bad replies do
not fall back. Missing journals/unknown lookup never mean zero execution.

Acceptance pins start/intent/marker-reply SHA and explicitly records a verified
native **route** outcome, `native_crop_lifecycle_verified=false`, no Teacher
preference label, and no formal training authorization. Original seed and lifecycle
records remain compatible; no seed preparation/dispatch record is fabricated.

## Bounded Validation And Evidence

guards check physical files and materialized JSON in a fresh non-reusing read
session, including CAS gzip blobs; an unchanged manifest or warm caller cache

new world capture, per-frame polling, global Teacher call or unbounded retry loop.
