# Original Partial Preparation Continuation

## Original Authority, Not Another Preparation Mutation

The accepted parent PR525 closes verified zero-dispatch controller stops. This
slice handles a different boundary: original preparation invoked once, original
marker mutation confirmed, but no completed preparation summary or queue.

`ContinueSeedPreparationAsync` requires the same v2 owner start, no preparation pin,
attached runtime or dispatch claim, and no retained execution artifacts. It reuses
the original intent builder/binder, original marker journal/reply-or-lookup and
full marker verifier. Missing intent/journal, missing lookup or a known bad local
reply never becomes permission to resend commit or native requests. Retained failed
summary identity must still match original intent; failed files are not overwritten.

The complete original base ledger must remain in original teacher-ledgers. The
original failed summary routes it when available; otherwise the retained complete
base is located and verified against the original immutable scope. It is not
fabricated from a later authority. The current complete marker readback must match
before compilation. Existing Get reconciliation semantics remain, not a global
side-effect-free-read claim.

## Append-Only Compilation Ownership

One durable owner continuation record binds admission/run/step/intent and the
original runtime's preparation-continuations namespace. Attempts are ordered,
append-only and directory-guarded; no cleanup or evidence replacement. The caller
supplies the trusted ORIGINAL compiler callback, not another policy/agent/executor.
It receives the original verified transfer marker/plan or planting marker/batch.
New output must retain compiled-seed-queue.json in that attempt.

An original or attempt queue already retained is checked with the original marker,
never replaced by a fresh good queue when known data is bad. Planting binds once:
the retained-queue branch binds for validation; a new compile lets the original
callback bind. The original eight-item mechanical batch/prefix and one-binding
rule remain. A pure compiler failure without a queue permits a distinct attempt;
unknown mutations/dispatch do not. No internal retry loop or unchanged automatic
replanning is added.

A completed continued-preparation.json contains the same original preparation
contract plus explicit recovery schema, original intent and transitive hashes.
Original failed summaries, inputs, journals, replies, queue and authority remain
pinned. Lost queue/view/owner-pin acknowledgements adopt verified retained evidence
without compiling or committing again. No summary success flag is proof by itself.

## Same Runtime And All Existing Recovery Consumers

The private original prepared certificate and owner pin carry an explicit path/SHA
reference tied to the continuation record. It is not a global reader fallback.
Default standalone/v1 preparation readers keep their original file and rejection
rules. New owned native recovery, prepared-only restoration and verified zero-stop
recovery explicitly consume the same pinned reference and re-run their original
full kernels. The same sealed purchase/transfer/planting transaction, settlement,
custody and fresh prefix are reconstructed. No second executor, source-hash rewrite,
per-seed queues, actor/profile relaxation or native-success/Teacher label.

This is a trusted host orchestration API, not a sandbox for arbitrary callbacks.
Automatic managed main entry stays disabled until original travel/maintenance/
native-save continuity and bounded native integration are connected. Exposing a
compiler callback does not authorize a model/API worker or keyboard control.
