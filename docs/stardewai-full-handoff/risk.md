# Risks

| risk id | risk | impact | mitigation | status |
|---|---|---|---|---|
| RISK-013 | The material graph reads all persistent player chests and classifies actor-owned, shared global, shared unowned, and other-player nodes. Shared/other nodes remain visible but default-denied. Save/player-scoped material reservations persist goal ownership, bind exact slots through candidate/compiler revisions, and are rechecked immediately before machine-crafting runtime input. Explicit shared grants are not implemented. | The AI no longer silently consumes another player's current resources or materials reserved for another controller goal through the implemented machine-crafting path. Intentional human sharing cannot yet be authorized, and future material-consuming executors must opt into the same dispatch gate. | Keep default deny. Require every new material-consuming executor to bind reservations and use typed dispatch readiness. Add versioned sharing grants and run a two-farmer isolated matrix before enabling shared nodes. | narrowed_open |
| RISK-014 | The dedicated host reaches the overnight `ShippingMenu`, but host-local draw suppression also prevents the nested native `SaveGameMenu.draw()` call which alone sets `hasDrawn=true`. Decompiled `SaveGameMenu.update()` refuses to start `SaveGame.Save()` until that flag is set, so the live server stopped after the native OK-button path at `Context: before save`; Bridge snapshots then timed out and the host-AI retry budget was exhausted. | The AI can finish a day but cannot persist or enter the next playable day while full draw suppression is enabled. The server container remains alive and CPU-bound while its API is unhealthy. | Keep the native ShippingMenu input path and native `SaveGame.Save()` coroutine. In dedicated-host draw-suppressed mode only, a Harmony prefix now restores the draw lifecycle signal by setting public `SaveGameMenu.hasDrawn=true` before native update. Do not claim recovery until a disposable overnight run proves save files advance, the menu closes, Bridge health returns, and the next action is verified. | static_fix_complete_deployment_and_runtime_proof_pending |
| RISK-012 | Machine demand classifies each learned machine dynamically and consumes current backlog, fleet timers, live crop waves, or active versioned outdoor-crop commitments. The shared ledger now also owns exact material reservations; both classes are save/player scoped, persistent, revision checked, auditable, cancellable, and compiler rebound. | Crop commitments still exclude greenhouse/Island/modifier/layout feasibility. Recurring animal output, future mining/smelting demand, machine placement/route cost, and full service execution can still change the answer. Treating this slice as complete long-horizon utility would underbuild or overbuild. | Preserve ledger revision/IDs through compilation and fail closed on drift. Upstream excludes only when no task, no proven covered-horizon deficit, and no first-craft requirement. Before broad training, add recurring supply projections, native placement/service chains, modifier/location commitments, dispatch-time ledger freshness, and craft/place/load runtime smokes. | narrowed_open |
| RISK-011 | Farmhouse purchases are irreversible and the new native Carpenter state machine has not yet been exercised in a disposable in-game save. | Dialogue timing could fail after native payment, or postcondition verification could report a false block while construction has already started. | Candidate, compiler, and runtime independently rebind endpoint, Robin presence, competing construction, house level, countdown, exact money/material tuple, and stand/path. Runtime uses only native map-action/dialogue callbacks and verifies money, material, unchanged immediate level, and countdown 3. Do not run on a human save; add isolated level-0 and level-1 fixtures before marking runtime complete. | open |
| RISK-007 | Runtime fishing replaced `Game1.input` with a custom `ControlledInputState`, but SMAPI 4.5.2 casts it to internal `SInputState` every update. | The game froze on the first cast frame, logs grew unboundedly, the executor request never completed, and no valid fishing training sample was produced. | Global/OS input replacement was removed. Runtime now reflects only the existing SMAPI `SInputState.OverrideButton(SButton.MouseLeft, ...)` entry point during `UpdateTicking`, preserving native charge, cast, hook, BobberBar physics, and cleanup. Source guards plus hidden ordinary and Lava Eel smokes passed with zero SMAPI errors. | closed |
| RISK-008 | High-difficulty fish are not mechanically guaranteed at low character fishing level even with optimal input and legal advanced equipment. | Treating every cast as certain could bias planning and training rewards; treating executor losses as crashes would also be wrong. | Preserve observed success/failure labels and transparent fishing level, rod, bait, tackle, fish difficulty, and outcome distribution. The Lava Eel smoke proves a successful native BobberBar path, but planner utility must retain the remaining character/equipment-dependent risk. | narrowed_open |
| RISK-001 | The new after-snapshot freshness wait was not exercised against a live E: SMAPI session in the first pass. | A live bridge/runtime timing edge could still produce `after_snapshot_fresh=false`, blocking trusted model training data. | Completed hidden/silent live runtime validation with applied and blocked movement episodes; both final artifacts have `after_snapshot_fresh=true` and `state_hash_changed=true`. | closed |
| RISK-002 | Historical applied movement artifact has equal before/after hashes even though executor changed `player.tile`. | Existing historical episode artifacts should not be used as final training examples for movement outcome learning. | Treat prior equal-hash movement artifacts as diagnostic only; regenerated final applied and blocked artifacts under `artifacts\hidden-training-final-*`. | closed |
| RISK-003 | Crop planting is only verified as a narrow single-tile executor slice, not as broad planting policy. | If a future planner exposes layout/crop-choice planting before candidate generation, seed acquisition, exceptions, and next-day outcomes are covered, the model could choose poor or impossible planting plans. | `farm.crop_catalog`, `player.seed_inventory`, and `current_location.planting_context` are transparent. `executor.plant_seed` now requires exact tile/seed `hard_rule_allows_planting=true` and has one isolated runtime smoke.
